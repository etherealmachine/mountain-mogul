# Fast-Forward Performance

Make 20× and the turbo speeds run smoothly. Step 10 of [[Demo]]: players will skip days to earn money, and the top speeds were jumpy in the playtest. Touches [[Snow]], [[Skiing]], and [[Rendering]].

## Why

Measured 2026-10-08 on the user's latest Boreal Goals Test save (388×388 cells, about 30 guests at peak), running the real game loop with `-screenshot -time-scale N -cpuprofile` plus temporary per-frame timers. Rendering is fine: about 4.5 ms of GPU and under 1 ms of CPU a frame. The jumpiness is three CPU costs, two of which grow with the map rather than the guests.

1. **Track fading hitches every 30 game-seconds.** `DemandSystem.maybePoll` (`sim/demand.go`) calls `SurfaceDetail.DecayTracks` each poll. The track texture is 20 pixels per cell, so 7760×7760 RGBA (about 240 MB), and the decay walks every pixel: 20–25 ms even when there are no tracks. With tracks it also calls `MarkAllDirty`, so the whole texture re-uploads (another 3.4 ms), on the same frame as item 2. That's a 30–37 ms frame every 1.5 s of wall time at 20×, and every 0.6 s at 50×. The burial in the daily weather update (`simulation.go`, "Bury skier tracks") uses the same scan, once a day.
2. **The snow textures rebuild for the whole map on any change.** `Terrain.SnowDirty` is one flag, set from about 25 places. When it's set, `Renderer.FlushSnowState` (`render/terrain_mesh.go`) recomputes all ~150k corners in `cornerSnow` and re-uploads both textures: 6.2–6.7 ms. Skiers packing snow, mogul growth, cats grooming, and snow guns set it, so at speed it fires nearly every frame, day and night. It was 47% of all CPU in an overnight 100× run with no guests. `cornerSnow` also derives each cell's snow values four times (once per corner it touches) and allocates about 3.6 MB per flush.
3. **Steering samples 168 hazard points per skier per step.** `sampleTactical` (`sim/skiing.go`) scores 7 headings × 8 segments × 3 corridor points, and each `hazardDensityAt` reads tree cover, nearby trunks, every lift tower, and nearby skiers. It runs on every 1/30 s step, about 14 µs per skier per step, and a frame has speed ÷ 2 steps (10 at 20×, 50 at 100×). About 4 ms a frame at 20× with 30 guests, 20 ms at 100×. It's the cost that grows with guests and speed, so it caps turbo and busier resorts.

A 20× frame on this save: about 4.5 ms GPU, 6.6 ms snow flush, about 4 ms sim; plus 23–28 ms every 1.5 s from item 1.

## Decisions

From the user, 2026-10-08: fade tracks in the shader; dirty cells instead of full flushes; then a hazard cache, which changes how skiers steer and needs testing afterwards; then parallel skier updates (added to the priority list the same day). Go's concurrency should be used where it helps, including splitting the sim from rendering (Concurrency, below).

## Steps

1. Done: **Fade tracks in the shader.** Each track pixel keeps the game minute it was last skied in its B and A bytes (`world.TrackClock`), and `terrain.frag` fades it by age (`trackAt`, at the old rate: 0.985 per 30 s). Filtering can't blend packed clock bytes, so the shader fetches the four nearest texels, fades each by its own clock, and blends them itself. Restamping a pixel first folds the fade since its old clock into its intensity, so the pair always describes the same visible track. `AgeTracks` does that for every pixel in the daily weather update, across cores, burying tracks by the day's snowfall at the same time; that keeps live clocks within a day of now, far from the 45-day wrap. The 30 s `DecayTracks` scan is gone. On the Goals Test save at 20×, the worst sim update fell from 34 ms to 2.7 ms; tracks still draw and fade (checked with the surface-detail overlay).
2. Done: **Dirty cells instead of full flushes.** `Terrain.SnowDirty` is gone. Writers mark the cells they change (`MarkSnowDirty`, `MarkSnowDirtyRect` around a snow gun), or `MarkAllSnowDirty` for snowfall, melt, avalanche checks, shedding, and the editor's snow layers. The terrain keeps a list of dirty 16-cell tiles (`world/snow_dirty.go`), and `Renderer.FlushSnowDirty` re-uploads just those tiles, or the whole map when everything is marked. `cornerSnow` derives each cell's values once and reuses buffers, and a whole-map flush splits rows across cores. Writes that never set the old flag (a skier wearing grooming down, lodge floors, `GroomCell`) now mark their cells, since a whole-map flush no longer hides them. On the Goals Test save, median update at 50× (busy day) fell from 8.6 to 0.9 ms, and at 100× overnight from 7.1 to 0.6 ms. The grooming overlay after a night of cat work matches the old build. Tile uploads still cost about 0.4 ms a frame at 50× (one upload call per tile); batching them is a possible follow-up.
3. Done: **Hazard cache.** Trunks: the terrain keeps a 1 m field of where each pixel's nearest trunk stands (`world/trunk_field.go`, 2 bytes a pixel, 7.5 MB on Boreal), and `TrunkHazardAt` measures the true distance to the nearest trunks of the four pixels around a sample. Against walking the trees, the mean error is 0.003 and almost no point is off by more than 0.02. A first version that stored the score itself, or the distance, and blended pixels read up to 0.3 too high just past each trunk's reach and between close trees. Tree edits mark their cells (`setCellTrees`), and the sim redraws just those at the start of each tick (`RefreshTrunkField`). Towers and other skiers are gathered once per decision within reach of the whole fan (`steerNear`), instead of searched at each of the 168 sample points; that gives the same answer. Steering time in a serial build roughly halved (hazard lookups 1.7 → 0.5 s over the same run, profiled with the first version of the field; the final one reads four pixels instead of blending them, similar cost). Behaviour: tree hits and falls unchanged within seed noise on two Boreal saves (the "15 degree slope with tree patch" testbed is also unchanged).
   Then **the skier grid refills every step** (`subTick`) instead of every frame, clearing only the buckets in use. Before, at 100× a skier could move about 16 m between refills and drop out of the buckets others searched, so skiers dodged each other less the faster the game ran: on the Goals Test save, falls a day were 0–1 at 200× but 0–2 at 4×. Now both speeds behave the same.
4. Done: **Steer skiers in parallel.** `tickGuests` runs its usual serial pass, but a skier's tick stops after perception and queues a job (`ski_parallel.go`). `decideSkiers` then runs `decide` for every queued skier across cores (at least 4 skiers per core; the calling goroutine takes a share), and the rest of each skier's tick (`applySkier`) runs in the original order. `decide` drew from the global RNG for its tie-break jitter and first turn side; each decision now gets its own small stream (`stepRand`), seeded from the global RNG in the serial pass, and the F3 overlay no longer uses up the game's random numbers. Checked with a throwaway headless driver on real saves: serial, normal, and forced-parallel builds end in identical states; the race detector found nothing over a game day; at 200× on the busiest save (46 guests) sim time per frame fell from 8.5 to 6.9 ms on average, with the worst 1% from 23 to 14 ms. The gain is held down by waking cores every 1/30 s step for only 20–30 skiers' work; it grows with crowd size, and the hazard cache (step 3) would shrink the per-skier work that's being split. Also fixed: restamping a track pixel in the same minute skips the fade math.
5. **More concurrency** if still needed: the rest of the list below, in order.

## Concurrency

The game already fans work out across cores in a few places (`world/horizon.go`, `sim/snowpack.go`, `geo/erosion.go`), on a 10-core machine. The main loop is one thread: `Scenario.Update` ticks the sim, then the renderer reads the world directly. Opportunities, most useful first:

- **Steer skiers in parallel.** After steps 1–3, steering is most of the sim. `decide` (and `sampleTactical` under it) only reads the world, apart from a shared scratch buffer (`s.hazardScratch`) that each worker would need its own copy of, and it draws no random numbers. So a step can decide every skier in parallel, then apply the results one by one in the usual order. The skier grid it reads is already built once per frame, so skiers already see each other's positions from the start of the frame. The one change is that a skier would no longer see snow packed by skiers earlier in the same step, which is negligible. Applying in a fixed order keeps seeded runs repeatable. It needs `tickGuests` split into a decide pass and an apply pass, since today planning, routing, and deciding are interleaved per guest. Gains roughly in step with cores for the steering part.
- **Split full-map loops across cores.** `cornerSnow` for a whole-map flush, hourly melt (`meltHour`), the daily weather update, and `ShedSnow` all walk every cell independently, the same shape as `snowpack.go`. Cheap, and it shortens the rarer whole-map frames that remain after step 2.
- **Run the sim on its own goroutine.** The sim would tick flat out on its own core while the main thread draws at a steady 60 fps, smoothing positions between sim updates. The frame rate would then stay steady at any speed, and the sim would fall behind rather than the screen stuttering. It's the biggest change. The renderer and UI read the world directly today (`DrawWorld`, panels, popups, the follow camera), and the player's tools change it, so it needs a snapshot of what's drawn (guests, chairs, cats, and snow regions to upload) handed over each frame, and player edits queued to the sim thread. GL calls stay on the main thread, but the snow textures' CPU half (`cornerSnow`) could move to the sim side. Worth doing only if turbo still drops frames after the above, or as part of the release build.
- **Build the horizon map in the background.** Rebuilding it after placing a lift takes 3.9 s of CPU on Kirkwood (already noted under Rendering and engine in [[Next Steps]]). It's already spread across cores but blocks the frame; building it in the background and swapping it in when done removes the hitch.
